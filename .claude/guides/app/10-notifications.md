# 10 — Notifications

## Purpose

The Notifications section covers two distinct concepts: the in-app notification bell that surfaces real-time alerts, and the notification preferences screen where users control which events trigger email and push notifications.

---

## Notification Bell (Global Shell)

The notification bell is rendered in the `SiteHeader` and is visible on every authenticated page. It shows a bell icon with a numeric badge indicating the count of unread notifications. The badge disappears when the count reaches zero.

**Behavior:**

- On mount (and on each route change), the app polls for the current unread count.
- Clicking the bell icon opens a panel (popover or slide-over) showing the most recent in-app notifications.
- Each notification in the list shows a brief message and a relative timestamp (e.g., "2 hours ago").
- Clicking a notification marks it as read and, if the notification links to a specific resource (e.g., a budget warning links to the budgets view), navigates to that resource.
- A **Mark all as read** button at the top of the panel marks all visible notifications as read and resets the badge to zero.
- The panel can be dismissed by clicking outside it or pressing Escape.

---

## Notification Types

In-app notifications are generated by the backend when specific events occur:

- **Budget warning** — spending in a budget category has exceeded the expected pace for the period.
- **Budget exceeded** — spending in a budget category has reached or exceeded the limit.
- **Goal milestone** — a savings goal has reached 25%, 50%, 75%, or 100% of its target.
- **Goal achieved** — a savings goal has been completed.
- **Invitation received** — a user has been invited to a shared wallet.
- **Invitation accepted** — someone accepted an invitation to the user's shared wallet.
- **Member joined** — a new member joined a shared wallet the user belongs to.
- **Member left** — a member left a shared wallet the user belongs to.
- **Settlement recorded** — a debt settlement has been recorded in a shared wallet.
- **Recurring generated** — a recurring transaction pattern has auto-generated a new transaction.
- **Friend request received** — another user sent a friend request.
- **Friend request accepted** — a sent friend request was accepted.

## Notification Preferences View

The notification preferences view (`/notifications`) is a dedicated settings-style page where users control their notification channels. It renders a `PreferencesForm` component.

**Fields:**

- **Email notifications** — a master toggle checkbox. When unchecked, no email notifications are sent regardless of individual type settings. When checked, individual email notification types are enabled/disabled via the fields below.

- **Push notifications** — a master toggle checkbox. When unchecked, no push notifications are sent. Push notifications require the browser to grant notification permission; if permission has not been granted, checking this toggle prompts the browser's permission request dialog.

- **Budget alerts** — a checkbox. Controls whether budget warning and exceeded events generate notifications.

- **Goal milestones** — a checkbox. Controls whether goal milestone and achieved events generate notifications.

- **Invitations** — a checkbox. Controls whether wallet invitation events (received, accepted) generate notifications.

- **Recurring updates** — a checkbox. Controls whether auto-generated recurring transaction events generate notifications.

Each individual type checkbox is governed by both the master toggle for its channel (email or push) and the type-specific toggle. A type is only active when both its channel master and the type toggle are checked.

**Actions:**

- **Save preferences** — submits the updated preferences to the API. On success, a success message is shown. While saving, the button shows a loading state.

**On mount:** The view fetches the current preferences from the server and pre-populates all checkboxes accordingly. This ensures the displayed state always reflects the server's authoritative state.
